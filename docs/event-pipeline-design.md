# Event-driven update pipeline: design

Status: proposed (2026-10-25), not built. Tracked in docs/TRACKER.md, Module 4 queue.

## 1. Why

The brief's Module 4 asks for "a closed loop where new milestones, supervision notes and amendments update the models
and vector indices". Today the loop is:

- a **weekly refresh job** (procintel.jobs, idle time) that re-fetches every source and runs every pipeline step in a
  fixed order (procintel.refresh: ingest → model tables → chunks → embeddings → tags → problem tags → firms → sector
  links → rating checks → evidence → exchange rates → prediction models → evaluation), then reloads the backend;
- a **daily drift check** that retrains the prediction models when enough packages were labelled since training;
- a **feedback review job** queued by every rating in the UI.

Two things are missing. Changes are only *found* inside the weekly refresh, so the system reacts to a new award notice
up to a week late; and when it reacts, it runs every step, even though most outputs did not change. Embedding and
tagging are already incremental (passages carry a text fingerprint), but nothing else is.

This design replaces "run everything on a timer" with: **track the state of each piece of data, turn every change of
state into a typed event, and run only the actions that depend on that event**. The job queue stays the execution
engine.

## 2. Concepts

```
  sources ──► detector ──► state store ──► events ──► rules ──► actions (jobs) ──► new state / outputs
  (WB APIs,     cheap        one row per      typed      which      registered      (tables, vectors,
   UI)          snapshot     entity + its     changes    actions    units of work    models) ──► reload
                             fingerprint                 to run     (idle-time queue)
                                     ▲                                     │
                                     └──────── actions may emit events ◄───┘
```

| concept | what it is | where it lives |
|---|---|---|
| **Entity type** | a kind of data we track: Project, Notice, Document, Passage, ContractAward, Indicator, Feedback | registered in code, one declaration each |
| **State** | for one entity: its key and a fingerprint of the fields we care about | table `entity_state` |
| **Detector** | per entity type: fetch a cheap snapshot, compare with stored state, emit events | one function per type |
| **Event** | a typed change: `Notice.added`, `Document.text_changed`, `Project.status_changed` ... with the entity key and old/new values | table `event_log` |
| **Action** | a registered unit of pipeline work, scoped to the entities in its events where possible | registry in code (like `jobs/handlers.py`) |
| **Rule** | "when this event (and condition) happens, run these actions" | defaults in code; additions/overrides in a rules file editable from the UI |

## 3. Entity types and their state

| entity type | key | fields in the fingerprint | source / detector |
|---|---|---|---|
| Project | project_id | status, closing date, sector, commitment, approval date | Projects API (one listing call per refresh) |
| Notice | notice_id | type, version, notice date, award date, price, suppliers | procurement notices API, newest first, stop at the last seen date |
| Document | doc_id | document type, text fingerprint | documents API listing (ICR now; ISR and restructuring papers later) |
| Passage | chunk_id | text fingerprint (exists: `text_hash`) | derived from documents by the chunker |
| ContractAward | wb_contract_number | signing date, amount, supplier | Finances One DS00005, per project |
| Indicator | (country, indicator, year) | value | indicators API (CPIA, WGI) |
| Feedback | feedback_id | rating, citation | the UI (already written to data/feedback.duckdb) |

Adding a new kind of data later means declaring one more entity type: table, key, fingerprint fields and a detector.
The state tracking, event log and rules then work for it unchanged.

## 4. Events

Generated by the detectors (and by actions, for derived data):

| event | emitted when |
|---|---|
| `<Type>.added` / `<Type>.removed` | a key appears or disappears |
| `<Type>.changed` | the fingerprint changes; carries the names of the changed fields |
| derived: `Package.award_changed`, `Passages.changed`, `Model.updated`, `Model.drift_detected`, `Data.updated` | emitted by actions when their outputs change |

Field-level events (`Project.status_changed`) are `<Type>.changed` with a field filter in the rule, so new field
events need no code.

## 5. Actions

Each action declares what it needs and what it emits, and runs as a job in the existing queue (idle time, pausable,
persistent, retried). Scoped actions take the keys from their events; aggregate actions rebuild something that
depends on all rows and are **coalesced**: many events in one detection run queue one rebuild.

| action | scope | today's code | emits |
|---|---|---|---|
| `update_packages` | the projects of the notices | model.build (split per project) | `Package.award_changed` |
| `fill_award_dates` | the projects of the contracts | contract_awards.fill_award_dates | `Package.award_changed` |
| `chunk_documents` | the documents | chunk.build (per document; ids already remapped) | `Passages.changed` |
| `embed_passages`, `tag_passages`, `problem_tag_passages` | the passages | embed / tag / problem_tag (already incremental) | — |
| `rebuild_evidence`, `rating_checks`, `sector_links` | the documents/projects | evidence, ratings, procurement_rating, sectors | — |
| `rebuild_firms` | aggregate | entities.build | — |
| `rebuild_benchmarks` | aggregate | stats (computed at reload) | — |
| `drift_check` → `retrain` | aggregate | jobs/handlers.py (exists) | `Model.updated` |
| `governance_scores` | the countries | model.build_cpia, wgi.build | — |
| `feedback_review` | aggregate | jobs/handlers.py (exists) | — |
| `reload_backend` | once per batch | server.reload_state (exists) | — |

## 6. Rules

Default rules ship in code; the UI adds, edits, disables and resets them. A rule:

```json
{"id": "awards-update-times",
 "on": "Notice.added",
 "where": {"field": "type", "op": "=", "value": "Contract Award"},
 "do": ["update_packages", "drift_check"],
 "enabled": true}
```

Default rules (initial set):

| on | where | do |
|---|---|---|
| `Notice.added`, `Notice.changed` | — | `update_packages` |
| `ContractAward.added` | — | `fill_award_dates` |
| `Package.award_changed` | — | `rebuild_benchmarks`, `drift_check` |
| `Document.added`, `Document.changed` | field `text` | `chunk_documents` |
| `Passages.changed` | — | `embed_passages`, `tag_passages`, `problem_tag_passages`, `rebuild_evidence`, `rating_checks` |
| `Project.changed` | fields `status`, `sector`, `closing_date` | `sector_links`, `rebuild_benchmarks` |
| `Indicator.added`, `Indicator.changed` | — | `governance_scores` |
| `Feedback.added` | — | `feedback_review` |
| `Model.drift_detected` | — | `retrain` |
| `Data.updated` (end of any batch that changed served data) | — | `reload_backend` |

### Rules in the UI

The Settings page gets a "Pipeline rules" panel: list rules with their last firing; add or edit one by choosing an
event type, an optional field condition and actions from the registered list; enable/disable; reset to defaults. Saved
like the settings profiles (data/pipeline_rules.json, not in git).

### Guardrails

- **A fixed menu of actions.** Rules choose registered actions only; no code or queries in rules.
- **Validation on save.** Unknown events or actions are refused; cycles (A emits what triggers A) are refused;
  costly actions (retrain, re-embed everything) are rate-limited (e.g. at most one retrain a day unless forced).
- **Dry run.** Before a rule is enabled, it is evaluated against the last 7 days of the event log: "would have fired
  37 times and queued: update_packages ×37 (coalesced to 6 runs), drift_check ×6".
- **Event log.** Every event, every rule firing and every action run is recorded, so "why did the prediction change?"
  has an answer ("14 award notices on 2026-11-02 → update_packages → retrain").
- **Defaults stay in code** and can always be restored.

## 7. Detection schedule

- A **change detection job** queued every hour (configurable) asks each source only for what is new since the last
  check (newest notice date, documents listing, project fields). It is cheap: a handful of requests.
- The **weekly full refresh** stays as a reconciliation: it rebuilds everything and fixes any state that drifted from
  the sources (a missed event, a bug). Its run is also logged as events, so the two paths agree.
- Feedback events come from the UI immediately (as today).

## 8. Storage

New tables (in a separate file data/pipeline.duckdb, written only by the worker, like data/jobs.duckdb):

| table | columns |
|---|---|
| `entity_state` | entity_type, key, fingerprint, fields (JSON), first_seen, last_seen |
| `event_log` | event_id, type, key, changed_fields, old, new, detected_at, batch_id |
| `rule_firing` | event_id, rule_id, actions, job_ids |

Actions write to the main database as the pipeline does today; the worker is the single writer.

## 9. Relation to existing code

| exists | becomes |
|---|---|
| procintel.jobs (queue, idle worker, handlers) | the execution engine; handlers become the action registry |
| text fingerprints on passages, incremental embed/tag | the Passage entity's state; unchanged |
| refresh.snapshot / diff | the first version of the detectors |
| refresh.run | the weekly reconciliation job |
| chunk.build id remapping | lets `chunk_documents` run per document without breaking ids |
| /admin/reload | the `reload_backend` action |

## 10. Build plan (each step usable on its own)

1. State store, event log and detectors for Notice, ContractAward, Project, Indicator; default rules; actions for
   packages, award dates, benchmarks, drift check, reload. Hourly detection job. Settings page: event log view.
2. Documents and passages: per-document chunk/embed/tag actions; ISRs and restructuring papers as new document types
   (the brief's "supervision notes and amendments").
3. Rules editable in the UI: rule panel, validation, dry run.
4. Weekly refresh reduced to reconciliation; remove the duplicated steps.

Verification for each step: a recorded fixture of source changes replayed through the detector, asserting the exact
events and jobs; a live run on the real sources comparing the event-driven result with a full refresh (same tables).

## 11. Open questions

- Detection interval: hourly is cheap for the APIs used; is a shorter interval useful for planners?
- Should ISRs and restructuring papers come in at step 2 or as their own task first?
- Who may edit rules in a multi-user deployment (pilot)? Today the Settings page has no sign-in.
- Retention of the event log (all, or the last N months).
